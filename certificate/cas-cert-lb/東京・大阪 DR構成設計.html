東京・大阪の冗長構成：
リージョン別の証明書と、DNSによる切替

社内のプライベート通信だけで使う業務システムの設計です。CAS、Certificate Manager、内部ALBを東京と大阪にそれぞれ置き、同じFQDNをCloud DNSで切り替えます。証明書は両方のリージョンで常に有効で、自動更新されます。切替で変わるのはDNSの応答だけです。

CASもCertificate Managerも両リージョンに作るCAプール、発行構成、証明書は同じリージョンでないと組み合わせられないため。
ルートCAは1つ、下位CAをリージョンごとに置く端末に配るルート証明書は1つだけ。東京が落ちても大阪の下位CAが自動更新を続ける。
グローバルにはできないCASにはグローバルがなく、リージョナルALBにはリージョナル証明書しか設定できない。LBを分ける要件がある以上、全リージョナルしか選べない。
DNS認証は使わないDNS認証は一般公開の証明書を使うときだけ必要。今回はプライベートCA（CAS）＋発行構成を使う。
切替はCloud DNSのフェイルオーバーポリシーで行う限定公開ゾーンで普段は東京を返す。東京の異常を検知したら大阪を返す。検知できない障害には手動で切り替える。

構成図：通常時と災対時の切り替え

ボタンで通常時と災対時を切り替えると、名前解決の結果と通信経路の変化が見られます。

通常時：名前解決と経路

  1. クライアントが test.sample.com を問い合わせます（VPC内はCloud DNS、オンプレからは受信転送を経由）。
  2. フェイルオーバーポリシーで、プライマリの東京ALBが正常と判定され、10.10.0.10 を返します。
  3. クライアントは東京ALBにHTTPSで接続します。ALBは cert-tokyo を提示します。
  4. 端末は、ルートCA → 下位CA 東京 → cert-tokyo の順に証明書をたどって検証し、接続を確立します。
  5. 東京ALBが業務サーバ #1・#2 に負荷分散します。

大阪は待機中です。ALB・証明書・サーバはすべて動いていて、証明書の自動更新も続いています。

災対時：名前解決と経路

  1. 東京ALBのヘルスチェックが失敗します（自動切替）。または、運用者がDNSレコードのプライマリを大阪に変更します（手動切替）。
  2. Cloud DNSが大阪ALBの 10.20.0.10 を返します。各端末に残っている古い応答は、TTL（30秒）が切れると更新されます。
  3. クライアントは大阪ALBに接続します。ALBは cert-osaka を提示します。
  4. 端末は、ルートCA → 下位CA 大阪 → cert-osaka の順に検証します。FQDNもルートCAも同じなので、端末側の変更はいりません。
  5. 大阪ALBが業務サーバ #3・#4 に負荷分散します。

変更が必要なのはDNSの応答だけです。証明書・ALB・CASには手を入れません。

切替時に変更する箇所：DNSだけ

事前に両リージョンを完成させておくのが前提です。災対時に設定を変えるのはDNSの1か所だけにしてあります。

ルートCAの仕組み：ルートは1つ、各リージョンには下位CAを置く

ルートCAは、1つの鍵とそれに対応する1枚の証明書でできた、1つの存在です。東京と大阪で別々に作ると、名前が同じでも鍵が違う「別のルートCA」になります。また、同じルートCAを大阪にコピーすることもできません。

ルートCA（東京に1つ）端末が信頼するのはここだけ
下位CA 東京→ cert-tokyo（test.sample.com）
下位CA 大阪→ cert-osaka（test.sample.com）

会社に例えると、ルートCAは本社の実印、下位CAは本社が認めた支社の印鑑です。端末は本社の実印だけを信頼していて、本社が認めた支社の印鑑もたどって信頼します。そのため、どちらの証明書を出されてもルートCAに行き着き、警告は出ません。

CASでの作り方

  1. 東京に、ルートCA用のCAプール（root-pool）とルートCAを作ります。
  2. 東京に下位CA用のCAプールを作り、そこで下位CAを作ります。発行元には東京のroot-poolを指定します。
  3. 大阪にも下位CA用のCAプールを作り、そこで下位CAを作ります。発行元には東京のroot-poolを指定します。CASは、リージョンをまたいだ発行元の指定ができます（--issuer-location=asia-northeast1）。GUIでは「CAを作成」→「下位CA」→「発行元」で選びます。
ルートCAを使うのは、下位CAを作るときと更新するとき（数年に1回）だけです。毎日の証明書の発行・自動更新は、それぞれの下位CAが行います。そのため、東京が被災してルートCAが使えなくなっても、大阪の業務は止まりません。
社内にすでにルートCAがある場合：例えばActive Directory証明書サービスのルートCAが全端末に配布済みなら、そのルートCAでCASの下位CAに署名してもらう方法もあります。CASで下位CAを作るときに「外部のCAで署名」を選ぶとCSR（署名要求）が出るので、社内のルートCAで署名して戻します。この方法なら、端末に新しいルート証明書を配らなくて済みます。

10.10.0.10と10.20.0.10は、LB自体のIP

内部ALBの「フロントエンドIP」（転送ルールのIP）で、仮想IP（VIP）とも言います。クライアントが接続する先で、DNSが返すのもこのIPです。特定のVMに付いたIPではなく、各リージョンのサブネットから割り当てます。

種類東京の例大阪の例役割
サブネット10.10.0.0/2410.20.0.0/24リージョンごとのIP範囲。VPCは全リージョン共通だが、サブネットはリージョンごとに作る
LBのフロントエンドIP10.10.0.1010.20.0.10クライアントが接続する先（DNSの応答）。静的な内部IPとして予約しておくのがおすすめ
業務サーバのIP10.10.0.21 / .2210.20.0.21 / .22LBの裏側。クライアントは直接接続しない
プロキシ専用サブネット10.10.100.0/2310.20.100.0/23LBの内部プロキシが使う範囲。サーバから見ると、通信元はこの範囲になる
サーバのファイアウォールに注意：サーバへの通信は、クライアントのIPではなく、LBのプロキシのIPから届きます。そのため、プロキシ専用サブネットからの通信を許可する必要があります。ヘルスチェック用のIP範囲も同様に許可します。フロントエンドIPは、GUIではALB作成時の「フロントエンドの構成」→「IPアドレス」で予約できます。

切替・切戻し手順

A. 自動切替（東京ALBそのものの障害）

  1. Cloud DNSが東京ALBを異常と判定し、自動的に大阪のIPを返し始めます。
  2. 運用者は、dig test.sample.com の結果が 10.20.0.10 になったことを確認します。
  3. 業務の疎通確認をします（大阪ALB経由で、証明書の警告が出ないこと）。

B. 手動切替（バックエンド障害・計画切替）

  1. レコードのプライマリを大阪に、バックアップを東京に入れ替えます（下のコマンド）。
  2. TTL（30秒）が過ぎてから、名前解決の結果と業務の疎通を確認します。
  3. オンプレのDNSキャッシュが残っている場合は、必要に応じてクリアします。
gcloud dns record-sets update test.sample.com. \
  --zone=zone-sample --type=A --ttl=30 \
  --routing-policy-type=FAILOVER \
  --routing-policy-primary-data=fr-osaka@asia-northeast2 \
  --routing-policy-backup-data-type=GEO \
  --routing-policy-backup-data="asia-northeast1=fr-tokyo@asia-northeast1" \
  --backup-data-trickle-ratio=0 \
  --enable-health-checking

C. 切戻し（東京の復旧後）

  1. 東京の業務サーバとデータの整合性が取れたことを確認します（アプリ側）。
  2. 東京ALB経由で直接疎通確認をします（curl --resolve test.sample.com:443:10.10.0.10 https://test.sample.com/）。
  3. 自動切替だった場合は、ヘルスチェックが正常に戻ると自動で東京に戻ります。手動切替だった場合は、プライマリを東京に戻します（下のコマンド）。
  4. 名前解決が 10.10.0.10 に戻ったことを確認します。
gcloud dns record-sets update test.sample.com. \
  --zone=zone-sample --type=A --ttl=30 \
  --routing-policy-type=FAILOVER \
  --routing-policy-primary-data=fr-tokyo@asia-northeast1 \
  --routing-policy-backup-data-type=GEO \
  --routing-policy-backup-data="asia-northeast2=fr-osaka@asia-northeast2" \
  --backup-data-trickle-ratio=0 \
  --enable-health-checking
年1回は切替訓練をしてください。リージョン専用の名前（簡単にする工夫①）を使うと、DNSを切り替えなくても大阪側を事前に確認できます。そのうえで手順Bで大阪に切り替えて、証明書の検証と業務の疎通を確認します。大阪の証明書が期限切れになっていないかも、このときに確認します。

構築手順（gcloudの例）

この順番で作ります。PROJECT_ID と PROJECT_NUMBER は置き換えてください。フラグは、実行前に公式リファレンスで確認をお願いします。

1. CAS：ルートCA（東京に1回だけ作る）

gcloud privateca pools create root-pool --location=asia-northeast1 --tier=enterprise
gcloud privateca roots create root-ca --pool=root-pool --location=asia-northeast1 \
  --subject="CN=Sample Root CA, O=Sample" --key-algorithm=ec-p384-sha384 --validity=P10Y
gcloud privateca roots enable root-ca --pool=root-pool --location=asia-northeast1

2. CAS：下位CA（東京・大阪）

# 東京
gcloud privateca pools create sub-pool-tokyo --location=asia-northeast1 --tier=enterprise
gcloud privateca subordinates create sub-ca-tokyo --pool=sub-pool-tokyo --location=asia-northeast1 \
  --issuer-pool=root-pool --issuer-location=asia-northeast1 \
  --subject="CN=Sample Sub CA Tokyo, O=Sample" --key-algorithm=ec-p256-sha256

# 大阪(発行元は東京のルート)
gcloud privateca pools create sub-pool-osaka --location=asia-northeast2 --tier=enterprise
gcloud privateca subordinates create sub-ca-osaka --pool=sub-pool-osaka --location=asia-northeast2 \
  --issuer-pool=root-pool --issuer-location=asia-northeast1 \
  --subject="CN=Sample Sub CA Osaka, O=Sample" --key-algorithm=ec-p256-sha256

3. Certificate Managerのサービスアカウントに、CAプールから発行する権限を付ける

gcloud beta services identity create --service=certificatemanager.googleapis.com --project=PROJECT_ID
for P in "sub-pool-tokyo asia-northeast1" "sub-pool-osaka asia-northeast2"; do set -- $P
  gcloud privateca pools add-iam-policy-binding $1 --location=$2 \
    --member="serviceAccount:service-PROJECT_NUMBER@gcp-sa-certificatemanager.iam.gserviceaccount.com" \
    --role="roles/privateca.certificateRequester"
done

4. Certificate Manager：発行構成と証明書（同じFQDN）

gcloud certificate-manager issuance-configs create ic-tokyo --location=asia-northeast1 \
  --ca-pool=projects/PROJECT_ID/locations/asia-northeast1/caPools/sub-pool-tokyo
gcloud certificate-manager certificates create cert-tokyo --location=asia-northeast1 \
  --domains="test.sample.com" --issuance-config=ic-tokyo

gcloud certificate-manager issuance-configs create ic-osaka --location=asia-northeast2 \
  --ca-pool=projects/PROJECT_ID/locations/asia-northeast2/caPools/sub-pool-osaka
gcloud certificate-manager certificates create cert-osaka --location=asia-northeast2 \
  --domains="test.sample.com" --issuance-config=ic-osaka

GUIで作る場合は、「証明書を作成」画面で、場所＝リージョン、Googleマネージド、認証局タイプ＝プライベートを選び、そのリージョンの発行構成を選択します。DNS認証の欄は出ませんが、それで正しい状態です。

5. 内部ALB：プロキシと転送ルール（大阪も同じように作る）

gcloud compute target-https-proxies create proxy-tokyo --region=asia-northeast1 \
  --url-map=um-tokyo --certificate-manager-certificates=cert-tokyo
gcloud compute forwarding-rules create fr-tokyo --region=asia-northeast1 \
  --load-balancing-scheme=INTERNAL_MANAGED --network=vpc-main --subnet=snet-tokyo \
  --address=10.10.0.10 --ports=443 \
  --target-https-proxy=proxy-tokyo --target-https-proxy-region=asia-northeast1 \
  --allow-global-access

6. Cloud DNS：限定公開ゾーンとフェイルオーバーレコード

gcloud dns managed-zones create zone-sample --dns-name="sample.com." \
  --visibility=private --networks=vpc-main --description="internal zone"
gcloud dns record-sets create test.sample.com. --zone=zone-sample --type=A --ttl=30 \
  --routing-policy-type=FAILOVER \
  --routing-policy-primary-data=fr-tokyo@asia-northeast1 \
  --routing-policy-backup-data-type=GEO \
  --routing-policy-backup-data="asia-northeast2=fr-osaka@asia-northeast2" \
  --backup-data-trickle-ratio=0 --enable-health-checking

7. 端末にルートCA証明書を配る

gcloud privateca roots describe root-ca --pool=root-pool --location=asia-northeast1 \
  --format="value(pemCaCertificates)" > sample-root-ca.pem

取り出したPEMを、GPOやMDMで端末の「信頼されたルート証明機関」に配布します。

構成を簡単にする工夫：一番効くのは「名前」より「コード化」

サブドメインを工夫しても、必要なリソースは減りません。証明書、CAプール、LBを同じリージョンで組む必要があるのは、リソースの配置に関する制約で、FQDNの付け方とは関係がないからです。そのため、構成そのものは「各リージョンに1セット」のまま変えず、扱いやすくする工夫を加えます。

工夫内容効果注意点推奨
B. 構築をコード化する（Terraformなど）1リージョン分のセット（CAS、Certificate Manager、ALB、サーバ）を1つのモジュールにまとめ、リージョン名とIPだけ変えて2回呼び出す「1リージョン分の構成 × 2」として作れる・説明できる。東京と大阪で設定がずれないコードを管理する体制が必要推奨
①リージョン専用の名前を証明書に追加する証明書のFQDNに、test.sample.com に加えて tokyo.test.sample.com / osaka.test.sample.com を入れ、DNSにも各リージョンのA レコードを作るDNSを切り替えなくても、各リージョンのLBを直接確認できる（切替訓練・切戻し前の確認）リソースは減らない（運用を楽にするための工夫）推奨
A. CAを3つから2つに減らす東京ではルートCAから直接証明書を発行し、大阪だけ下位CAを置くCAが1つ減り、月額料金と管理の手間が減るルートCAの鍵を毎日の発行に使うことになり、ベストプラクティスから外れるリスクを受け入れられるなら
②ワイルドカード証明書（*.sample.com）にする証明書の名前をワイルドカードにする名前を追加するときの作業は楽になるリージョンごとに1枚ずつ必要なのは変わらない。対象の範囲が広くなりすぎる効果は薄い
C. 証明書を自作の仕組みで更新するCAプールを東京だけに置き、Cloud Schedulerと関数で、証明書を発行して東京・大阪の両方にアップロードするCASが1リージョンで済む自作の更新処理を保守する必要がある。東京が被災すると更新が止まる非推奨

B. コード化のイメージ（Terraform）

# modules/region_stack: 1リージョン分(CAプール・下位CA・発行構成・証明書・ALB・サーバ)
module "tokyo" {
  source      = "./modules/region_stack"
  region      = "asia-northeast1"
  name        = "tokyo"
  lb_ip       = "10.10.0.10"
  fqdns       = ["test.sample.com", "tokyo.test.sample.com"]
  root_pool   = google_privateca_ca_pool.root.id   # 共通のルートCA
}

module "osaka" {
  source      = "./modules/region_stack"
  region      = "asia-northeast2"
  name        = "osaka"
  lb_ip       = "10.20.0.10"
  fqdns       = ["test.sample.com", "osaka.test.sample.com"]
  root_pool   = google_privateca_ca_pool.root.id
}

# DNS(フェイルオーバー)は共通部分として1回だけ定義
# primary = module.tokyo.forwarding_rule / backup = module.osaka.forwarding_rule

①リージョン専用の名前を使った確認方法

# 証明書(各リージョンに、共通名とそのリージョン専用の名前を入れる)
gcloud certificate-manager certificates create cert-osaka --location=asia-northeast2 \
  --domains="test.sample.com,osaka.test.sample.com" --issuance-config=ic-osaka

# DNS(通常のAレコード。ルーティングポリシーはなし)
gcloud dns record-sets create osaka.test.sample.com. --zone=zone-sample \
  --type=A --ttl=300 --rrdatas=10.20.0.10

# 切替前に大阪側だけを確認
curl -v https://osaka.test.sample.com/
業務の接続先は、引き続き test.sample.com だけです。リージョン専用の名前は、運用者が確認に使うためのもので、利用者には案内しません。

注意点

  • リージョンを揃える：CAプール、発行構成、証明書は同じリージョンに作ります。大阪の証明書を東京のCAプールから発行することはできません。
  • 証明書マップは使わない：リージョナルの内部ALBでは、ターゲットHTTPSプロキシに証明書を直接設定します。
  • ルートCAの置き場所：東京が被災すると、ルートCAは使えなくなります。それでも大阪の下位CAは発行を続けられるので、運用への影響はありません。新しい下位CAを作るのは、東京が復旧してからにします。
  • 有効期間の目安：ルートCAは10年程度、下位CAは5年程度にします。下位CAの期限が近づいたら、新しい下位CAを作って入れ替えます（これは自動更新されないので、計画的な作業が必要です）。
  • 証明書の監視：証明書は自動更新されますが、Cloud Monitoringで期限と更新失敗のアラートを設定しておくと安心です。特に、普段使わない大阪側は見落としやすいので注意してください。
  • 証明書のピン留めは避ける：アプリが証明書そのものをピン留めしていると、大阪に切り替えたときに接続エラーになります。信頼の基準はルートCAにします。
  • CASの階層とコスト：ここではEnterprise階層の例を挙げています。CAごとに月額料金がかかるので、全部で3つ（ルート1・下位2）の費用を見込んでください。
  • オンプレからの名前解決：受信転送の受け口は、東京と大阪の両方を登録します。オンプレとの回線（VPN・Interconnect）も、大阪側を用意しておく必要があります。
