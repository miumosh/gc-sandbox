# 検証の作業履歴（時系列）

2026-11-10（UTC）に行った作業と、そのときに各監視がどう反応したかを 1 つの表にまとめた。
- 時刻はすべて **UTC**（日本時間はプラス 9 時間）
- 出典は、保存したログ（[`logs/20261110T1710Z/`](logs/README.md)）と、Monitoring API で取得したインシデント一覧
- 監視 ID の意味は [`README.md`](README.md) の 3 章を参照

## 0. この表で一番伝えたいこと: 「VM を止めても、ヘルスチェックログは出ない」

| 状況 | VM の状態 | ヘルスチェックログ | A1 / A3（ヘルスチェック監視） | 該当する行 |
|---|---|---|---|---|
| Scheduler で 1 台を停止 | TERMINATED | **出ない** | **発報しない** | #9, #21, #26 |
| Scheduler で **2 台とも停止** | 2 台とも TERMINATED | **出ない** | **発報しない** | #10, #11 |

| ファイアウォール削除でヘルスチェックが届かない（VM は稼働中） | RUNNING | 約 16 秒後に 2 台とも `HEALTHY→UNHEALTHY` が出る | 発報する | #32 |
| VM を起動 | RUNNING | `UNHEALTHY(UNKNOWN)→UNHEALTHY(TIMEOUT)→HEALTHY` が出る | 発報しない（条件で除外） | #15, #22, #29 |

→ ヘルスチェックログは、**「VM は動いているが、ヘルスチェックに応答しない」とき** にしか出ない。VM が停止すると、その VM はヘルスチェックの対象から外れ、UNHEALTHY への遷移が記録されないまま ALB の振り分け先から消える（`get-health` の一覧からも消える）。2 台とも止まっても同じで、このとき ALB は 503 を返し続けるが、ヘルスチェックログは 1 件も出ない。全台停止を検知できたのは A2（503 のログ）と A4（Uptime Check）だった。

## 1. 表の見方

| 列 | 意味 |
|---|---|
| web-1 / web-2 | VM の状態 / ALB から見た状態（H = HEALTHY、U = UNHEALTHY、外 = ヘルスチェック対象外。停止中は get-health の一覧から消える） |
| HC ログ | ヘルスチェックログが出たかどうかと、その内容 |
| ALB 応答 | 試験クライアント（2 秒ごと）から見た ALB の応答 |
| A1〜A7, S1〜S3 | 各監視の反応。**発報** = インシデントが作られた / 回復 = インシデントがクローズした / なし = 発報する可能性があったのに発報しなかった / 空欄 = 関係なし / 未作成 = その時点でポリシーがまだない / 集約 = 既存のインシデントにまとめられ、新しい通知が出なかった |

- **A1** ヘルスチェックログ（ログ）
- **A2** ALB の 5xx（ログ）
- **A3** ヘルスチェックのログベース指標（指標）

- **A6** バックエンド別リクエスト数の途絶（指標）

- **S3** 監査ログの ERROR（ログ）

## 3. この時系列から分かること

1. **VM 停止（#9〜#11、#21、#26）では、台数に関係なくヘルスチェックログが 1 件も出ない**。ログが出たのは、起動時（#2、#15、#22、#28）、アプリ停止時（#16、#19）、ファイアウォール削除でヘルスチェックが届かなくなったとき（#32）だけ。いずれも **VM が RUNNING の状態** だった
2. **2 台とも停止したとき（#11）**: ALB は約 5 分間、すべてのリクエストに 503 を返し続けたが、ヘルスチェックログは 0 件で、A1 / A3 は発報しなかった。検知できたのは A4（Uptime Check、#13）と A2（503 のログ、#14）
3. **VM 停止の検知に使えたのは** A7（約 1 分）、A6（約 7 分）、A5（約 8.7 分）（#21）
4. **VM 停止でも、まれに 503 が出る**（#21 の 18:07:55）。シャットダウン中にアプリが先に止まると、ヘルスチェックが UNHEALTHY と判定する前に ALB がその VM へ振り分けてしまい、`connection_refused` の 503 になる。1 回目（#9）はタイムアウトだけで、503 は出なかった
5. **ログベースアラートは、同じラベルのインシデントが開いている間は新しく通知しない**（#16 の A1、#19 と #21 の A2）
6. **Scheduler の失敗**は、S3 → S1 → S2 の順に検知された（#7、#24）。存在しない VM を指定したときも、権限を外したときも、結果は 403
7. **A5 は短時間の停止でも、遅れて発報することがある**（#30。約 1.5 分の停止に対し、起動から約 5.5 分後に発報）。原因は未確認
