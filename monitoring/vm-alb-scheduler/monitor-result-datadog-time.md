# Datadog 監視の検知時間の比較

[monitor-result-datadog.md](monitor-result-datadog.md) の 5 つのモニター（M1〜M5）が、事象の発生から何分で通知されるかを比較したもの。

> 注意: Datadog への取り込みとモニターは、今回の検証では動かしていない。この資料の Datadog の時間は、GCP 側の実測値（[RESULTS.md](RESULTS.md) 4 章）とモニターの設定から計算した **推定値**。導入時に実測して見直す。

---

## 1. 結論

| ID | 役割 | 監視 | 検知する事象 | リクエストが必要か | 通知までの目安（Datadog、推定） | 参考: GCP 側の実測 |
|---|---|---|---|---|---|---|
| M1 | 補助 | ALB のリクエストログ 5xx | 全台停止、業務 URL のエラー、ALB の異常 | **必要** | 停止の操作から **約 1.5〜3.5 分**（最初の 503 から約 1〜2.5 分） | A2: 正確な値は取れていない |
| M2 | 土台 | Compute Engine の Uptime | VM 停止（1 台ずつ） | 不要 | 警告 **約 10 分**／危険 **約 15 分** | A5（途絶 180 秒の条件）: 約 8.7 分 |
| M3 | 土台 | Cloud Scheduler のジョブの実行ログ | 起動・停止ジョブの失敗 | 不要 | ジョブの実行から **約 1〜3 分** | S1: 約 35〜49 秒 |
| M4 | 土台 | Compute Engine の監査ログ | 起動・停止 API の失敗 | 不要 | 操作から **約 1〜3 分** | S3: 約 20〜49 秒 |
| M5 | 土台 | ALB のヘルスチェックログ | アプリの停止・ハング（VM は動いている） | 不要 | アプリ停止から **約 1〜3 分** | A1: 約 23 秒 |

- ログの監視（M1・M3・M4・M5）は分単位、指標の途絶の監視（M2）は 10 分以上かかる
- 全台停止のとき、M1 は M2 より **約 8〜12 分早い**（M1 約 1.5〜3.5 分、M2 警告 約 10 分）。ただし M1 はリクエストがあるときだけ
- アプリの停止・ハングは M5 が約 1〜3 分で拾う。M1 はリクエストがあっても数件の 5xx（警告）にとどまり、M2 は反応しない

---

## 2. 早さに差が出る理由

| 観点 | M1（5xx のリクエストログ） | M2（Uptime 指標） |
|---|---|---|
| 何を見るか | 「エラーが起きた」というログ | 「値が来なくなった」こと |
| 監視の種類 | 事象が起きたことを数える | 値が届かないことを判定する |
| 発報の条件 | 直近 5 分に 1 件以上（警告）／20 件以上（危険） | 直近 10 分の平均が 30 以下（警告）／0 以下（危険） |
| 評価範囲（5 分・10 分）の意味 | ログを **数える範囲**。5 分待つわけではない | 停止時間が **積み上がるのを待つ時間**。5 分（警告）／10 分（危険）止まるまで平均が下がらない |
| 発報できるタイミング | 1 件目のログが届いた直後の評価 | 平均値が閾値まで下がったとき |
| 取り込みの遅れの扱い | 届いた時点で数える（遅らせる設定なし） | `evaluation_delay: 300` で、評価そのものを 5 分遅らせている |
| 差の大きな要因 | – | 「止まった時間を待つ」5〜10 分と、evaluation_delay の 5 分 |

M5（ヘルスチェックログ）も M1 と同じ「事象が起きたことを数える」監視なので早い。さらに、ヘルスチェックは利用者のリクエストではなく ALB が 5 秒ごとに送る確認なので、リクエストが無い時間帯でも動く。

GCP 側の検証でも同じ傾向だった。

| 方式の種類 | GCP 側の方式 | 実測の遅延 |
|---|---|---|
| ログで発報 | A1 ヘルスチェックログ、A7 監査ログ、S1 Scheduler ログ、S3 監査ログの ERROR | 約 20 秒〜1 分 16 秒 |
| 値の途絶で発報 | A5 uptime の途絶、A6 バックエンド別リクエスト数の途絶 | 約 5.9〜8.7 分 |

## 3. 検知時間の内訳

### 3.1 M1: ALB のリクエストログ 5xx（全台停止の場合）

| # | 区間 | 目安 | 根拠 |
|---|---|---|---|
| 1 | 停止の操作 → 最初の 503 | 約 1 分 | 実測 54 秒（RESULTS.md 3.3、T2） |
| 2 | ALB → Cloud Logging にログが出る | 数秒〜数十秒 | GCP のログアラートが、ログ記録から 13〜45 秒で発報した実績 |
| 3 | Log Router シンク → Pub/Sub → Dataflow → Datadog | 数十秒〜1〜2 分 | Dataflow はまとめて送るので、その待ち時間が乗る（未検証） |
| 4 | Datadog のログモニターの評価 | 〜1 分 | 1 分ごとに評価 |
| | **合計** | **停止の操作から約 1.5〜3.5 分** | |

### 3.2 M2: Compute Engine の Uptime（VM 1 台の停止）

モニタークエリ: `avg(last_10m):default_zero(avg:gcp.gce.instance.uptime{...} by {instance_name}) <= 0`、`evaluation_delay: 300`

| # | 区間 | 警告（≦ 30） | 危険（≦ 0） | 説明 |
|---|---|---|---|---|
| 1 | 停止の操作 → 停止完了 | 約 1 分 | 約 1 分 | 実測 約 50 秒（RESULTS.md 3.7） |
| 2 | 10 分の平均が閾値まで下がるのを待つ | 5 分 | 10 分 | 停止した 1 分ごとに 0 が積み上がる。平均 30 ＝ 5 分停止、0 ＝ 10 分停止 |
| 3 | evaluation_delay | 5 分 | 5 分 | 評価範囲が「5〜15 分前の 10 分間」になる。GCP 指標が Datadog に届くまでの遅れを吸収するため |
| 4 | Datadog の評価間隔・誤差 | 〜1 分 | 〜1 分 | 停止直前の 1 分の値が 60 未満になることもある |
| | **合計** | **約 10〜12 分** | **約 15〜17 分** | |

### 3.3 参考: GCP の A5 が約 8.7 分かかった理由（推定）

A5 は「uptime の値が 180 秒届かなかったら発報」という条件（`monitoring.tf` の `a5_vm_uptime_absent`）。評価範囲が広かったのではなく、**GCP の指標が見えるようになるまでの遅れ** が主な原因。

| # | 区間 | 目安 |
|---|---|---|
| 1 | stop の実行 → 停止完了（監査ログで実測） | 約 50 秒 |
| 2 | 最後の値の 1 分間（uptime は 60 秒ごと） | 〜1 分 |
| 3 | GCE の指標が見えるようになるまでの遅れ（公式ドキュメントで最大 240 秒） | 〜4 分 |
| 4 | 途絶の継続時間（`duration = 180s`） | 3 分 |
| 5 | 評価してインシデントを作るまで | 〜1 分 |
| | **合計**（実測 8 分 42 秒と合う） | **約 8〜10 分** |

### 3.4 M3・M4: Scheduler のジョブ実行ログ・監査ログ（起動・停止の失敗）

| # | 区間 | 目安 | 根拠 |
|---|---|---|---|
| 1 | ジョブの実行 → 失敗のログが出る | 数秒〜数十秒 | 403 は API の呼び出しですぐ返る。GCP 側の発報は S1 で約 35〜49 秒、S3 で約 20〜49 秒 |
| 2 | Log Router シンク → Pub/Sub → Dataflow → Datadog | 数十秒〜1〜2 分 | M1 と同じ経路（未検証） |
| 3 | Datadog のログモニターの評価 | 〜1 分 | 1 分ごとに評価 |
| | **合計** | **約 1〜3 分** | |

### 3.5 M5: ALB のヘルスチェックログ（アプリの停止・ハング）

| # | 区間 | 目安 | 根拠 |
|---|---|---|---|
| 1 | アプリ停止 → UNHEALTHY に変わる | 約 10 秒 | ヘルスチェックは 5 秒間隔、2 回連続の失敗で UNHEALTHY（`lb.tf` の `check_interval_sec = 5`、`unhealthy_threshold = 2`） |
| 2 | 遷移ログが Cloud Logging に出る | 数秒〜十数秒 | GCP 側（A1）はアプリ停止から約 23 秒で発報した |
| 3 | Log Router シンク → Pub/Sub → Dataflow → Datadog | 数十秒〜1〜2 分 | M1 と同じ経路（未検証） |
| 4 | Datadog のログモニターの評価 | 〜1 分 | 1 分ごとに評価 |
| | **合計** | **アプリ停止から約 1〜3 分** | |

- 通知上の「回復」は、遷移ログから 5 分たったときに来る。実際に回復したかどうかとは関係ない（ログは状態が変わったときに 1 件出るだけのため）

## 4. 検知できる範囲の違い

| 事象 | M1 5xx（補助） | M2 Uptime（土台） | M5 ヘルスチェック（土台） | 補足 |
|---|---|---|---|---|
| VM 2 台とも停止（リクエストあり） | ◯ 約 1.5〜3.5 分 | ◯ 約 10 分（警告） | ✕ | 最初に気づけるのは M1 |
| VM 2 台とも停止（リクエストなし。夜間など） | ✕ | ◯ 約 10 分（警告） | ✕ | 5xx はリクエストが来ないと出ない。ヘルスチェックログは VM 停止では出ない |
| VM 1 台だけ停止 | △ 出ても警告 1 回（または出ない） | ◯ 約 10 分（警告） | ✕ | ALB がもう 1 台に振り分けるので 5xx がほぼ出ない。検証では停止中に 503 が 1 件だけ（RESULTS.md 3.7） |
| アプリが停止・ハング（1 台。VM は動いている） | △ 数件の警告（リクエストが無ければ出ない） | ✕ | ◯ 約 1〜3 分 | M5 だけが確実に拾う |
| アプリが停止・ハング（2 台とも。リクエストなし） | ✕ | ✕ | ◯ 約 1〜3 分（VM ごと） | |
| ヘルスチェックの URL は正常だが、業務の URL で 5xx | ◯（リクエストがあれば） | ✕ | ✕ | ヘルスチェック専用の URL に変えた場合に起こりうる（今は `/` を確認） |
| どの VM が止まったか | ✕（ALB 全体の件数） | ◯（VM 別に評価） | ◯（インスタンスグループ別に評価） | |

- 死活の土台は M2（VM の停止）と M5（アプリの停止）。どちらもリクエストの有無に依らない
- M1 は「サービスとして困っている状態」を早く知るための補助。全台停止なら M2 より早いが、リクエストが無いと発報しない。M1 は M2・M5 の代わりにならない

## 5. M2 を早くする方法

| 方法 | 変更内容 | 通知までの目安 | 注意点 |
|---|---|---|---|
| 現在の設定 | 警告 30、evaluation_delay 300 秒 | 警告 約 10 分／危険 約 15 分 | – |
| 警告の閾値を上げる | 警告を 42 に（3 分停止で警告） | 警告 約 8 分 | 取り込みの揺らぎで 1〜2 点欠けると誤検知しやすくなる（1 点欠けで 54、2 点欠けで 48） |
| evaluation_delay を減らす | 300 → 120 秒（例） | 警告 約 7 分／危険 約 12 分 | 実際の取り込みの遅れより短いと、届いていない値を 0 と見なして誤検知する。導入時に遅れを測ってから決める |
| 上の 2 つを両方 | 警告 42、evaluation_delay 120 秒 | 警告 約 5 分 | 誤検知のリスクも両方乗る |
| M4 系の監査ログで補う | stop 完了の監査ログ（成功）も監視する（GCP 側の A7 に相当） | 約 1〜3 分 | API 操作による停止しか拾えない（ゲスト OS 内の shutdown やホスト障害は出ない）。計画停止でも反応する |

## 6. 導入時に確認すること

| 項目 | 確認方法 | 見直す設定 |
|---|---|---|
| ログの取り込みの遅れ | Datadog の Log Explorer で、ログの時刻（`timestamp`）と取り込まれた時刻の差を見る | 遅れが 5 分を超える場合、M1・M3・M4・M5 の評価範囲（`last("5m")`）から外れて数えられない可能性があるので、範囲を広げる |
| 指標の取り込みの遅れ | VM を 1 台止めて、Datadog 上で `gcp.gce.instance.uptime` の値が途切れるまでの時間を見る | M2 の `evaluation_delay` |
| 実際の通知時間 | 検証の T1（1 台停止）・T2（全台停止）・T5（権限なしで停止）・アプリ停止と同じ操作をして、通知が届いた時刻を記録する | この資料の推定値 |
