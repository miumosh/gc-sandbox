CAS・CAプール・CA・Certificate Manager：
構成パターンの選び方

東京・大阪のリージョナル内部ALBに、同じFQDN（test.sample.com）の証明書を自動更新で配置する、プライベート通信のみの構成が前提です。用語の関係、仕様上の制約、5つの構成パターン、ベストプラクティスを1枚にまとめました。

CAプールは最低2つ（東京と大阪）CAプール、発行構成、証明書は同じリージョンに揃える必要があるため。

用語と関係：「印鑑」と「窓口」と「保管庫」

CASは認証局（CA）を動かす役所、CAプールは窓口、CAは印鑑です。Certificate Managerは、LBに設定する証明書の保管庫です。この2つのサービスを結ぶのが、発行構成です。

用語何か置き場所たとえ
CASGoogle Cloudが提供する、自分専用の認証局を作って動かすサービス—印鑑を作って保管する役所
CAプールCAを入れる入れ物。証明書の発行はプールに依頼する。発行のルールや権限はプール単位で設定するリージョン必須（グローバルはない）窓口
CA証明書に署名する実体。1つの鍵と1枚の証明書からなる所属するプールと同じ印鑑
ルートCA信頼の大元。自分で自分に署名した証明書を持ち、端末の信頼ストアに入れる—本社の実印
下位CAルートCAに署名されたCA。日常の証明書の発行・更新を担当する—支社の印鑑
社内ルートCA社内ですでに運用しているCA（AD CSなど）。全端末に配布済みのことが多いGoogle Cloudの外すでに使っている本社の実印
Certificate ManagerLBに設定する証明書を管理するサービスグローバル／リージョナル証明書の保管庫
発行構成Certificate Managerと、CASのCAプールを結びつける設定証明書・CAプールと同じリージョン発行依頼書
信頼ストア端末が信頼するルートCAの一覧各端末知っている実印の一覧

仕様上の制約：どのパターンでも守る4つのルール

CAプールはリージョンの指定が必須グローバルなCAプールはありません。
CAプール、発行構成、証明書は同じリージョンに置く大阪の証明書を東京のCAプールから発行することはできません。
リージョナルALBには、同じリージョンの証明書を直接設定するグローバル証明書や証明書マップは使えません。
下位CAの発行元は、別リージョンにあってもよい大阪の下位CAを、東京のルートCA（または社外のCA）で署名できます。

構成パターン：同じ枠組みで5つを比べる

どの図も、上が端末の信頼ストア（またはGoogle Cloud外のルートCA）、左が東京、右が大阪です。白い枠はルートCA、青い枠はALBに設定する証明書、ピンクは注意点です。

標準：3プール・3CA 社内ルートCAがない場合の基本形

良い点

  • ベストプラクティスどおり。ルートCAの鍵を使う機会が最小限
  • 端末に配るルートは1つ
  • 東京が被災しても、大阪で更新が続く

気になる点

  • CAが3つ分の料金がかかる
  • Googleは、ルートCAを専用のプロジェクトに置くことを推奨している（根拠）

③ 社内ルートCAを使う：2プール・2CA 最適

良い点

  • CA2つで、ベストプラクティスも守れる
  • 端末への配布が不要（配布済みのルートを使う）
  • ルートがGoogle Cloudの外にあるので、被災の影響を受けない

気になる点

  • 下位CAを作るときと更新するとき（数年に1回）に、社内ルートCAでCSRに署名する作業が必要

① 東京はルートCAから直接発行：2プール・2CA コスト優先なら

良い点

  • CAが1つ減る
  • 端末に配るルートは1つのまま

気になる点

  • ルートCAの鍵を、日常の発行・更新のたびに使う（危険性の解説）
  • ルートCAに問題が起きると、全体を作り直す必要がある

② ルートCAを東京・大阪で別々に作る：2プール・2CA 特別な理由がなければ不採用

良い点

  • 東京と大阪が完全に独立する

気になる点

  • 端末に配るルートが2つになり、配布と期限の管理が2倍
  • ルートCAの鍵を、日常の発行・更新のたびに使う

NG：1つのプールにルートCAと下位CAを同居させる 採用しない

起きること

  • プールは、プール内の有効なCAから発行するCAを自動で振り分ける
  • 東京の証明書が、ルートCAから直接だったり下位CAからだったりして、ばらばらになる

結果

  • ①の欠点を抱えたまま、CAは3つ分の料金がかかる
  • 構成がわかりにくく、トラブルの原因を追いにくい

ルートCAの鍵を「日常的に使う」とは：パターン①・②の危険性

これまで「毎日使う」と書いてきましたが、正確には「証明書を発行・自動更新するたびに使う」という意味です。Googleマネージド証明書は有効期間が90日で、期限の約1か月前に更新が始まります。そのためパターン①では、東京の証明書1枚につき、年に6回ほどルートCAの鍵で署名することになります。

1. ルートCAの鍵が使われる回数（5年間の試算）

標準・③
約2回下位CAを作るとき（東京・大阪の2回）だけ。更新は5年に1回程度
①
約31回大阪の下位CAを作るときの1回に加えて、東京の証明書を発行・更新するたびに使う（約60日ごと）

試算の前提：証明書は東京1枚、下位CAの有効期間は5年、Googleマネージド証明書は約60日ごとに更新される。証明書やFQDNが増えると、①の回数はその分だけ増えます。

3. 具体的な危険性

危険性何が起きるか標準・③①・②根拠
ルートCAで署名できる経路が、常に開いている①では、Certificate Managerが日常的にルートCAのプールへ発行を依頼します。そのため、ルートCAのプールに発行の権限を付けたままにする必要があります。権限の設定ミスや誤操作があると、ルートCAが署名した証明書が意図せず発行されるおそれがあります。◎
ルートのプールは、下位CAを作るとき以外は誰も触らない		×AWS Private CA best practices（ルートCAから直接発行すると、アクセスを絞れなくなる）／Certificate Manager best practices（ルートCAの使用を監視・アラート対象にする）
問題が起きたときの影響範囲が全体に及ぶルートCAに問題が起きると、その下のすべての証明書が信頼できなくなります。新しいルートCAを作って全端末に配り直す必要があり、それが終わるまで新しい証明書も発行できません。◎
問題は下位CAの範囲で止められる		×CA settings（ルートCAの変更は難しいため、保護を推奨）／AWS Private CA best practices
失効させて切り離すことができないルートCAは自分で自分に署名しているので、失効させるという手段がありません。信頼をやめるには、全端末から削除するしかありません。下位CAなら、失効させて作り直せます。◎
下位CAは失効もローテーションも簡単		×Create a subordinate CA（下位CAはルートCAより失効・ローテーションが容易）
用途ごとに制約を分けられない発行ポリシーはCAプール単位で、名前制約はCAの証明書に設定します。ルートCAから直接発行すると、「下位CAへの署名」と「サーバ証明書の発行」に同じプール・同じCAの設定がかかるので、用途ごとに絞り込みにくくなります。○△Overview of policy controls
冷静な評価：CASの鍵はHSM（専用のハードウェア）で保護されていて、外に取り出すことはできません（CAS best practices）。そのため、鍵そのものが盗まれる可能性は低いです。現実的なリスクは、「権限の設定ミスや誤発行」と「問題が起きたときの復旧範囲の大きさ」の2つです。社内限定の小規模なシステムで、ルートCAのプールの権限を厳しく管理し、ルートCAの使用を監視するアラートを入れられるなら、①を選ぶのも現実的な判断です。

選び方：質問2つで決まる

Q1. 社内にルートCA（AD CSなど）があり、全端末に配布済みですか？
はい → パターン③社内ルートCAで、東京・大阪の下位CAに署名します。
いいえ → Q2へ
Q2. ルートCAの鍵の管理について、厳しいセキュリティ要件がありますか？
はい（または迷う） → 標準（3プール）迷うなら、ベストプラクティスどおりの標準を選びます。
いいえ、コストを優先したい → パターン①ルートCAの鍵を日常的に使うリスク（解説）を受け入れられる場合だけ。

各項目の右に、根拠となるドキュメントを付けました。Google公式はGoogle Cloudのドキュメントに書かれている推奨事項、一般原則はGoogleのドキュメントには明記がなく、他社（AWS・Microsoft）のドキュメントで示されているPKI全般の考え方、目安は公式の根拠がない、本資料独自の推奨値です。

CAの階層と配置

  • ルートCAは専用のGoogle Cloudプロジェクトに分け、発行用（下位）のCAプールは別のプロジェクトに置く。発行用のプールは、リージョン・環境（本番・検証）・用途ごとに分ける
    Google公式 Certificate Manager best practices
  • CAの階層は、できるだけ単純に保つ（ルートCA → 少数の下位CA → 証明書）
    Google公式 Certificate Manager best practices
  • CASはリージョナルなサービスだが、あるリージョンのルートCAで、別のリージョンの下位CAに署名できる（東京のルートCAで大阪の下位CAに署名する構成の根拠）
    Google公式 Certificate Manager best practices
  • ルートCAは変更が難しい（変えるには、それを信頼している全端末を更新する必要がある）ため、保護する
    Google公式 Determine CA settings
  • 下位CAは、ルートCAより失効やローテーションが簡単。発行の用途ごとに下位CAを分けられる
    Google公式 Create a subordinate CA
  • ルートCAは下位CAへの署名にだけ使い、サーバ証明書は下位CAから発行する（パターン①・②を推奨しない理由）
    一般原則 AWS Private CA best practices／Microsoft Certificate Services best practices（ルートCAはオフラインで保護する）
  • 外部のCA（社内ルートCAなど）で、CASの下位CAに署名できる。CASが出力するCSRに外部のCAで署名し、署名済みの証明書をCASに取り込む（パターン③の根拠）
    Google公式 CA Service concepts

CAプール

  • CAプールは、プール内の有効なCAの間で、証明書の発行を振り分ける。役割の違うCA（ルートと下位）を同じプールに入れない（NGパターンの根拠）
    Google公式 Overview of CA pools
  • 発行用のCAには、CAプールを使う。CAプールは、発行ポリシーとIAMポリシーを共有するCAの集まり
    Google公式 Certificate Manager best practices
  • ほとんどの場合はEnterprise階層を使う。DevOps階層は失効に対応しておらず、発行した証明書も保存されないので、失効の必要がない短命な証明書にだけ使う
    Google公式 CAS best practices／Select the operation tiers
  • 発行ポリシーで、発行してよいドメイン・鍵の種類・有効期間を制限する。CAの証明書に名前制約（例：sample.com 配下だけ）を設定し、許可していないドメインへの発行を防ぐ
    Google公式 Overview of policy controls

鍵

  • CAの鍵はCloud HSMで保護され、取り出せない。特別な要件がなければ、Googleが所有・管理する鍵を使う
    Google公式 CAS best practices
  • ECDSAは、性能と安全性のバランスが最も良い。CAの有効期間に関係なく、CAの鍵を定期的にローテーションする手順を用意しておく
    Google公式 CAS best practices
  • 有効期間の目安：ルートCAは10年程度、下位CAは3〜5年程度
    目安 Googleのドキュメントに明記はありません。組織のポリシーに合わせて決めてください

権限（IAM）

  • 1人に複数のロールを同時に付けない。幅広い権限が必要なら、カスタムロールを作る
    Google公式 CAS best practices
  • Certificate Managerのサービスエージェントには、下位CAのプールに対する roles/privateca.certificateRequester だけを付ける。ルートCAのプールを操作できる人は最小限にする
    目安 最小権限の原則を、この構成に当てはめたもの

監視と更新

  • ログを使ったアラートを設定する：ルートCAの使用、証明書の期限が近い、CAの期限まで30日、証明書の作成失敗が多い、CAの鍵（KMS）の問題
    Google公式 Certificate Manager best practices
  • Googleマネージド証明書は有効期間90日で、期限の約1か月前に自動更新が始まる。下位CAそのものは自動では更新されないので、期限前に入れ替える計画を立てておく
    Google公式 Certificate Manager best practices
  • 普段使わない大阪側も同じように監視し、年1回の切替訓練で、証明書が有効で検証が通ることを確認する
    目安 DR運用としての推奨
